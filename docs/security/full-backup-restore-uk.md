# Повне аварійне відновлення CRM і ledger

Для організацій із ledger підтримується **повна база PostgreSQL + усі файлові сховища**. Частковий JSON-імпорт/експорт через вебінтерфейс відхиляється з HTTP 409 до видалення даних. Це зберігає незмінність журналів, складені зовнішні ключі, SQL-тригери, ідентифікатори користувачів та зв'язки між організаціями. Відновлення окремої організації цим інструментом не виконується.

## Перед резервним копіюванням

Зупинити всі процеси запису: застосунок, cron, import workers, інтеграції та зовнішніх DB-клієнтів. Сам скрипт не зупиняє і не запускає сервіси. `--writers-stopped` — явне підтвердження оператора. Залишити PostgreSQL запущеним. Потрібні Python 3 і Docker CLI з доступом до контейнера БД. Використовується встановлена в цьому контейнері версія pg_dump/pg_restore.

Шляхи файлових сховищ — шляхи **на машині, де запускається скрипт**. Для Docker volumes спочатку надати їх цьому середовищу як доступні каталоги. `--uploads` має вказувати на фактичний uploadsRoot застосунку (звичайно `DATA_ROOT/uploads`). Якщо `LEDGER_ATTACHMENT_STORAGE` або `LEDGER_IMPORT_STORAGE` перевизначено, ОБОВ'ЯЗКОВО передати відповідні прапорці. Без них використовуються підкаталоги `ledger-documents` і `ledger-imports` усередині uploads.

```sh
python3 scripts/full-backup.py \
  --db-container crm-db --db-user crm --database crm \
  backup --writers-stopped \
  --uploads /srv/crm/data/uploads \
  --output /srv/backups/crm-2026-10-27
```

Якщо після зміни `DATA_ROOT` залишилися файли в старому `data/uploads`, додати `--legacy-uploads /старий/шлях/data/uploads`. Вони об’єднуються в архів uploads; за однаковим шляхом перевагу має поточний uploads, як у застосунку.

Для окремих сховищ додати `--ledger-attachment-storage /srv/ledger-documents --ledger-import-storage /srv/ledger-imports`.

Вихідна папка повинна бути новою та розташованою поза файловими сховищами. Вона створюється з правами 0700, файли — 0600. Архів містить персональні дані й секрети з БД: зберігати його у захищеному зашифрованому backup-сховищі з обмеженим доступом. Шифрування та доставка до віддаленого сховища не входять у цей локальний інструмент.

У папці будуть `database.dump`, три файлові архіви та `manifest.json`. Manifest записується останнім: його відсутність означає незавершений backup. Скрипт автоматично знаходить **всі таблиці public**, а не фіксований список ledger-моделей; перевіряє кількість та контрольні суми рядків до/після копіювання, SHA-256 архівів і кожного файла. Зміни під час backup спричиняють помилку. Для великих БД перевірка рядків може тривати довго; не замінює зупинку записів.

## Відновлення

Використовувати лише довірений backup. Маніфест контролює цілісність, але не є цифровим підписом. pg_restore виконує SQL зі збереженої бази.

Відновлювати в **нову назву БД** та **новий каталог файлів**, бажано в окремий тестовий контейнер тієї самої версії PostgreSQL. Скрипт ніколи не виконує DROP DATABASE або `--clean`; якщо база чи каталог уже існують, операція відхиляється. Користувач PostgreSQL має мати право створення БД.

```sh
python3 scripts/full-backup.py \
  --db-container crm-restore-db --db-user crm --database crm_restored \
  restore --backup /srv/backups/crm-2026-10-27 \
  --output-files /srv/crm-restored-files
```

Перед створенням БД перевіряються контрольні суми всіх архівів і файлів, забороняються symlink, абсолютні шляхи, traversal та повтори записів. PostgreSQL відновлюється однією транзакцією. Дані всіх таблиць звіряються з manifest. Тригери та constraints повертаються штатним pg_restore; додаток не отримує механізму обходу незмінності ledger.

Ознака повного успіху — `result: PASS` і `restore-verified.json` у новому каталозі. Невдалий target залишається для діагностики, але його не можна використовувати; початкова БД не змінюється.

Відновленому застосунку призначити:

- DATABASE_URL нової БД;
- uploadsRoot → `<output-files>/uploads`;
- LEDGER_ATTACHMENT_STORAGE → `<output-files>/ledger-documents`;
- LEDGER_IMPORT_STORAGE → `<output-files>/ledger-imports`.

Перевірити в ізольованому середовищі авторизацію, залишки, платежі, документи та завантаження вкладень. Не запускати відновлені cron/інтеграції проти реальних зовнішніх сервісів до перевірки конфігурації. Перемикання production виконується окремо; цей скрипт його не робить.
