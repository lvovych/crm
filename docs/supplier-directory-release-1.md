# Supplier directory — Release 1 review

## Scope

Adds a tenant-scoped supplier directory, contacts, bank accounts, payment terms,
archive, permissions, audit history and optional preferred supplier on inventory.
Legacy supplier strings and product URLs remain intact. Preferred supplier is a
catalogue preference, not evidence of a purchase. No stock or financial postings
are generated by these changes.

Every supplier can provide both parts and services. No specialization flags,
form controls, list columns or filters restrict that capability. Legacy type
parameters are ignored. The legal form (company/person/entrepreneur/unknown) is
independent of what a supplier provides and remains available.

## Rollout

1. Back up the database and rehearse the additive Prisma migration on a copy.
2. Deploy with `SUPPLIER_DIRECTORY_ORGANIZATIONS` empty (default: disabled).
3. Enable one pilot organization by its ID; assign supplier permissions explicitly.
4. Verify create/edit/archive, tenant boundaries, inventory editing and backup restore.
5. Upload a normalized Carbook snapshot on `/suppliers/import` for review.
6. Review eligible suppliers, document evidence, uncertain records and duplicate candidates.

The import page writes staging records only. Execution uses the operator SQL
generator below after rehearsal and approval. Disable the feature flag to stop rollout;
retain the additive tables and legacy fields. Do not drop populated tables to roll back.

## Source contract

`src/features/suppliers/Lib/preview.ts` defines the versioned JSON contract. Uploads
are limited to 8 MiB and 2,000 suppliers. Source account + external supplier ID is
the stable identity; names are never used for automatic merging. Existing mappings
are reported rather than overwritten. Re-upload refreshes the staging assessment.

The cutoff must be midnight in the workshop timezone, three calendar years before
the snapshot date. For a 2026-11-03 snapshot this is 2023-11-03. Only posted,
nonzero goods receipts, supplier services, returns, payments and refunds qualify.
Orders, drafts, deletions, cancellations, opening balances and adjustments do not.
Missing evidence, incomplete coverage and orphan movements prevent a complete
assessment. Old outstanding balances alone do not qualify for migration.

The future supplier API adapter must produce the same normalized contract, preserving
source account, document identities, original dates, statuses and completeness flags.
The preview is not a general accounting import and does not import balances.

## Approved migration preparation

The approved selection is 84 of 150 reviewed cards. Exclude 57 without qualifying
movement, 7 inactive cards with movement and 2 own sole-proprietor cards. Preserve
each remaining Carbook ID as a separate supplier, including the four possible
duplicate pairs. Approval does not authorize merging with an existing CRM record.

`approvedPlan.ts` validates an exact private approval manifest against a normalized
snapshot. It rejects missing approved IDs, contradictory exclusions and mismatched
source accounts/periods; inactive cards, renamed cards, missing movement evidence,
CRM conflicts and ambiguous mappings block readiness. Extra source cards are never
selected. Existing source mappings are skipped, never overwritten. Checksums bind
the plan to the parsed snapshot and approval content.

For an offline preparation (no database connection or writes):

```sh
node --import tsx scripts/prepare-supplier-import.ts snapshot.json approved-84.json ORGANIZATION_ID plan.json
```

The output is created exclusively with owner-only permissions. Offline output
always requires a target-database check and cannot declare execution readiness.
The library's `ready` flag means its supplied inputs pass preparation checks; it
is not an authorization token. The operator SQL executor verifies the target
organization owner and existing source links inside its transaction. Database
uniqueness enforces source identities. Do not trust a client-supplied plan.

The reviewed document examples prove selection, not complete transaction history.
Do not mark complete historical coverage or invent a latest-activity date. The
seven missing goods quantities and an additional replacement receipt were read
from posted source documents. All 84 general/requisites tabs were checked; the
seven legal records across four cards were read, including bank/address details.
Duplicate legal records are normalized within their source card; separate supplier
cards are never merged. Unknown legal forms stay unknown. Explicit source zero-day
terms stay zero. No balances, stock or payments are imported.

Generate SQL locally (the generator never connects to a database):

```sh
node --import tsx scripts/build-supplier-rehearsal.ts snapshot.json approval.json ORGANIZATION_ID OWNER_ID rehearsal.sql
```

Default output refuses any database except `supplier_rehearsal`. Execute it only
in the isolated copy after applying the PR migrations. Check first-run counts,
repeat-run skips, injected-error rollback, existing-table fingerprints and a
dump/restore round-trip. For approved production execution, append the exact
snapshot checksum from the successful rehearsal as a sixth argument. That output
requires database `crm`; it is not a remotely callable application endpoint.
Take a fresh backup, check the target organization and existing identities again,
then execute once with `psql -X -v ON_ERROR_STOP=1`. The transaction verifies owner
membership, serializes same-organization imports, refuses unexpected existing
directory data and keeps source identity/checksum mappings. Repeats skip linked
records without overwriting edits. The import run records approval and evidence.

Keep snapshots, approvals, generated SQL, supplier names, contacts and bank data
outside Git. Only generic code, synthetic tests and aggregate results belong here.
