# Перевірка повернень постачальникам — 18.11.2026

## Облікові правила
- Чернетка не змінює склад, борг, каси чи оплату вихідних накладних.
- Під час проведення повторно перевіряються організація, постачальник, стан і дата приходу, відкритий період, доступна кількість та одиниця виміру.
- Один документ може містити рядки різних накладних одного постачальника.
- Проведення атомарне: усі складські рухи й кредит постачальника створюються разом або повністю відкочуються.
- Повернення зменшує загальне сальдо постачальника; не створює оплат накладних і не показується як грошовий аванс.
- Повернення послуг коригує закупівельну собівартість пов’язаної роботи без складського руху.
- Повтор запиту не створює повторного списання. Редагування чернетки перевіряє версію.
- Номер документа постачальника зберігається окремо. Проведений документ не можна переписати повторним запитом.
- Причина обмежена чотирма дозволеними значеннями на клієнті та сервері.

## Додане покриття
- Конкурентне проведення двох чернеток на останню одиницю товару або послуги.
- Закриття періоду, скасування приходу, сторнування обліку приходу та зміна одиниці після збереження чернетки: документ лишається чернеткою без часткових записів.
- Незмінність номера постачальника при повторному проведенні з іншими даними.
- Збереження номера, версії та ідентифікатора при редагуванні форми.
- Повтор відправлення після втрати відповіді з тим самим ідентифікатором.
- Захист форми від подвійного відправлення.
- Тисяча часткових повернень за різними цінами: сума дорівнює початковій, жодне повернення не від’ємне.
- Перевищення кількості, некоректна історична сума, недопустима причина та задовгий номер документа.
- Контракт ARM64 workflow: одна збірка, незмінний digest для деплою, відхилення некоректного digest.

Існуючі інтеграційні перевірки додатково покривають ізоляцію організацій і постачальників, спільний складський залишок кількох накладних, повернення після видалення товару з наряду, округлення послуг, оплачені приходи, незалежне сальдо та відновлення резервної копії.

## Продуктивність і подальші межі
Проведення завантажує лише запитані рядки, а не всі позиції вихідних накладних та їхні оплати.

Список повернень і список доступних позицій постачальника поки не мають серверної пагінації. На великому архіві потрібні серверний пошук, пагінація та вимірювання часу/обсягу відповіді на репрезентативній базі. Поточні тести не є навантажувальним тестом.

Проведення серіалізується фінансовим блокуванням організації та блокуванням постачальника. Це захищає облік від перегонів, але одночасні операції можуть чекати одна на одну; змінювати блокування без окремих конкурентних перевірок не слід.

## Реліз
Hetzner CAX21 використовує ARM64. Release workflow збирає тільки linux/arm64 на ubuntu-24.04-arm. Тег версії та службовий тег вказують на один результат збірки; деплой використовує digest. Архітектура комп’ютера користувача браузера на це не впливає. Старі образи не видаляються, production цим комітом не змінюється.
